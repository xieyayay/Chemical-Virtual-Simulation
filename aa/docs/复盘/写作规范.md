# 写作规范 · 六段式

> 这份文档规定「每一页怎么写」。写之前先读这一页，写的时候对照最后一节的验收清单。

## 一、为什么要有规范

接手一个 2758 个资产、131 个蓝图的工程，最容易发生的不是「看不懂」，而是**看懂了但写不出来**。规范的唯一目的：让每一页都能被三个月后的你、以及下一个接手的人，在 30 秒内判断「这页讲什么、能不能信、下一步做什么」。

## 二、六段式结构（每页固定）

顺序不能乱，缺任何一段都算没写完。

| 段 | 标题 | 要求 | 长度 |
|---|---|---|---|
| ① | `## 一句话结论` | 这页的核心判断，一句话。不是目录，不是背景 | 1–3 行 |
| ② | `## 机制` | 它怎么运转的：时序 / 数据流 / 职责边界。**必须配一张图** | 300–800 字 + 1 图 |
| ③ | `## 本项目实例` | 落到具体资产路径、ini 段、节点树。**每个论断后面跟出处** | 200–600 字 |
| ④ | `## 坑与反例` | 你踩过的、或读代码发现的错误写法，写「症状 → 根因 → 改法」 | 每条 3 行起 |
| ⑤ | `## 自测` | 3 道题，两题「是什么/在哪」、一题「如果改成 X 会怎样」 | 3 题 |
| ⑥ | `## 延伸` | 下一步该读哪个文件、哪个官方页面、哪条命令 | 3–5 条 |

### 页面开头固定两行

```markdown
# 页面标题

> 一句话概括这页解决什么问题。

**状态**：草稿 / 已核对 / 已冻结　**最后核对**：2026-11-19　**适用版本**：UE 5.7.4
```

`状态` 三档的含义：

- **草稿** —— 写完了但没跑过验证，可能错
- **已核对** —— 关键数字与资产路径都对照过实际工程
- **已冻结** —— 三个月内不会再变（配置、规范类）

## 三、出处等级（每条论断都要带）

| 标记 | 含义 | 举例 |
|---|---|---|
| `〔O〕` | 官方文档 / release notes | https://dev.epicgames.com/documentation/en-us/unreal-engine/gameplay-framework-in-unreal-engine?application_version=5.7 |
| `〔M〕` | 本机实测：RemoteControl 导出、日志、ini 原文、编辑器截图 | `Config/DefaultEngine.ini` 第 N 行；`Saved/Logs/aa.log` |
| `〔I〕` | 推断，未验证 | 必须写「待验证」并给出验证方法 |

规矩：**没有 `〔O〕` 或 `〔M〕` 的句子，只能是「我的判断」并显式注明**。宁可留空，不要编。

## 四、版本漂移检查（本项目已发生）

站点现有页面的头部写的是 **UE 5.4.4**，而工程实际是 **5.7**（`aa.uproject` 的 `EngineAssociation=5.7`，`Docs/HANDOVER.md` 记 5.7.4 / CL 51494982）。这类漂移还有两处已确认：

| 位置 | 文档写的 | 实际 |
|---|---|---|
| `docs/getting-started/project-overview.md` | UE 5.4.4 | 5.7 |
| 同上 · 渲染段 | `r.Shadow.Virtual.Enable=1` | 已改为 `0`（改用 CSM） |
| `docs/index.md` badge | `UE 5.4.4 · 全蓝图实现` | 5.7 |

所以每页必须写 `适用版本`，且**改配置类内容时，回头看一眼所有提到该配置的页面**。

## 五、命令与数据必须可复现

写「有 50 个交互点」不算证据。要写成：

```text
〔M〕BP_interact_* 共 50 个（AssetRegistry 过滤 /Game/UI/BP/interact，
    导出时间 2026-11-19，见 Saved/ue_audit/01_blueprints.json）
```

数字旁边给「怎么数出来的」。截图旁边给「什么时候截的、哪个 build」。

## 六、代码块规范

蓝图节点用 `blueprint` 语言标记（站点已配 pymdownx.highlight，会按普通文本高亮）：

````text
```blueprint
Event BeginPlay
  → Get Game Instance → Cast To BP_ChemistryGameInstance
  → Branch (IsValid?) → True: Set PlayMode
```
````

规则：

1. **节点名写英文原名**（`Cast To`、`Branch`、`Sequence`），中文只做注释
2. **连线用 `→`**，分支用 `├─` / `└─`
3. 一个代码块只讲一条流程，超过 15 行就拆

配置文件用 `ini`，控制台命令用 `text`，Python 用 `python`。

## 七、图片规范

- 放 `docs/images/<章节>/`，命名 `章节-序号-内容.png`，例：`interact-03-widget-level.png`
- 截图前打开 `Show > Collision` / `Show > Navigation` 等需要的可视化层
- 每张图下面必须有一句说明它「证明了什么」，不能只放图
- 正文里的图片点击可放大（站点自带 lightbox），不需要额外设置

## 八、长度与节奏

| 页面类型 | 目标长度 | 一次写完的时间 |
|---|---|---|
| 知识卡（`kb/`） | 40–80 行 | 20–30 分钟 |
| 系统页（`systems/`） | 200–400 行 | 2–3 小时 |
| 参考页（`assets/`、`build/`） | 100–250 行 | 1–2 小时 |
| 样板/总览页 | 300–500 行 | 半天 |

**一次只写一页**。写完立刻 `mkdocs serve` 看一眼，然后打勾。不要把三页一起写——那是永远写不完的开始。

## 九、验收清单（每页写完逐条勾）

- [ ] 开头两行齐全（状态 / 最后核对 / 适用版本）
- [ ] 六段齐全，顺序正确
- [ ] 每条关键论断带 `〔O〕` 或 `〔M〕`
- [ ] 至少一张图（自绘流程图也算，用代码块画）
- [ ] 至少一条「坑」，写清症状→根因→改法
- [ ] 3 道自测题，其中 1 道是推演题
- [ ] 所有资产路径可以直接粘到编辑器搜索框里搜到
- [ ] `mkdocs build --clean` 无警告（尤其是链接失效）
- [ ] 在 `docs/复盘/路线图.md` 的状态表里把这一页改成 ✅

## 十、不要做的事

1. 不要写「UE 是什么」这类通识——那是知识卡的事，且只写与项目相关的部分
2. 不要复制官方文档段落——给链接 + 一句你自己的话
3. 不要凭记忆写数字——`Saved/ue_audit/` 里有导出结果，直接查
4. 不要在正文里写「TODO 待补充」就算了事——要么留 `> ★ 待补：<具体缺什么、怎么补>`，要么先不建这个文件
